# Decision Log

## [M4] Project-Scoped Learning & Memory (Phase 1.2)
**Decision:** Migrate flat-file JSON memory (\personal_brain_memory.json\) to \ContextNodeDAO\ using explicit node types.
**Rationale:** The legacy system lacked user and project isolation, posing a security risk (data leakage) and contextual confusion for the upcoming multi-agent runtime. By moving rules and feedback into \context_nodes\, memory becomes natively queryable and strictly project-scoped.
**Semantics:** Established \LEARNING_RULE\, \FEEDBACK_LOG\, and \SCANNED_FILE_LOG\. Decided not to invent new ContextEdges as \projectId\ implicitly bounds the context appropriately for now. Legacy data is migrated to the \default\ project namespace.

## [M3] SEC-001 Remediation & Legacy API Route Delegation
**Decision:** Refactor \ackend/server.js\ endpoints (\/api/projects\, \/api/chat\) to enforce strict ownership verification via \ProjectAuthorizationService\.
**Rationale:** Client-provided \userId\ cannot be trusted. By enforcing that the requesting user strictly matches the project's \user_id\, we resolve the High Risk BOLA/IDOR vulnerability identified in Phase 1.2 discovery.

## [M2] Canonical Workspace Definition
**Decision:** Create \WorkspaceManager\ as the single source of truth for physical file path resolution.
**Rationale:** Prevents path-traversal vulnerabilities and unifies how \projectService\, \devServerManager\, and \	erminal\ resolve workspaces. Relegates \workspace_files\ to a legacy mirror, establishing physical files as canonical source code truth.

## [2F.1] Retrieval Contracts & SQLite Encapsulation
- **Decision:** Python i-engine will NOT read the SQLite Universal DB directly.
- **Rationale:** Prevents multi-process DB locks, schema coupling, and deployment fragility. Node.js maintains absolute ownership of canonical data.
- **Result:** RAG synchronization will occur across an explicit API/Event boundary. Retrieval results are treated strictly as derived pointers (source_entity_id) and validated against tenant constraints (project_id).

## [2F.2] Canonical Entity Hashing & Push Sync
- **Decision:** Use deterministic SHA-256 hashes generated by Node.js for tracking index state, rather than relying on Python to compute hashes. Sync happens via stateless HTTP pushes.
- **Rationale:** Keeps the absolute truth of "what the content is" on the Node side. If a file is modified via the WorkspaceManager, Node calculates the hash and dictates to Python what to index. This guarantees the derived index perfectly mirrors the Universal DB without coupling processes.

## [2F.3] Embeddings & Derived Vector Index
- **Decision:** Use ChromaDB local persistent storage in Python with LlamaIndex SentenceSplitter.
- **Rationale:** Minimizes external dependencies, guarantees deterministic chunking, natively isolates tenants via metadata filters ($eq: project_id), and provides explicit delete() operations for idempotent stale chunk removal.
- **Result:** Complete end-to-end embedding pipeline. Node.js dictates index pushes; Python purely handles chunking and storage into the local Chroma DB directory.

## [2F.4] Hybrid Retrieval & Ranking Engine
- **Decision:** Implemented a weighted ranking formula (Semantic 0.6, Keyword 0.3, Authority 0.1) and L2 distance normalization (1 / (1 + d)).
- **Rationale:** Normalizes disparate retrieval methods into a unified scale for deterministic Top-K bounding and deduplication.
- **Result:** Fully autonomous retrieval endpoint isolated strictly by project metadata, returning deduplicated candidate entities.

## [2G.3] AgentCoordinator, Supervisor Runtime & Structured Result Persistence
- **Decision:** Establish `AgentCoordinator` as a thin orchestration layer and restrict `SUPERVISOR` role strictly to `orchestration.manage`. Store worker results in canonical `agent_handoffs.result_json` with `ResultValidator`.
- **Rationale:** Prevents security bypasses (Supervisor cannot write files or execute shell directly), enforces tenant isolation and worker depth limits (max 3), guarantees delegation idempotency, and provides a structured JSON envelope for worker results.
- **Result:** Fully passing 182-test regression across all architectural components. In-process mutation lock is classified as acceptable for single-node phase.

## [2G.4] Advanced Multi-Agent Verification & Arbitration
- **Decision:** Implement `MultiAgentVerifier` with least-privileged `VERIFIER` role (read-only, no workspace mutation) and `SupervisorArbitrator` for deterministic arbitration (`COMPLETE`, `REPAIR`, `WAITING_FOR_USER`, `FAILED`).
- **Rationale:** Prohibits treating worker self-claims ("I fixed it") as proof of task completion; verifies evidence freshness (rejects stale hashes and cross-project artifacts), bounds repair cycles (max 3), and cleanly routes to `WAITING_FOR_USER` without multi-agent debate or infinite loops.
- **Result:** Complete 197-test regression across all multi-agent, runtime, checkpoint, RAG, and isolation layers with 0 failures.

## [AF.2] Runtime Profile Architecture — LIGHT / STANDARD / SCALE
- **Decision:** Define three runtime profiles (LIGHT for mobile/low-resource, STANDARD for desktop, SCALE for server/distributed) sharing the same logical application contracts but differing in resource utilization.
- **Rationale:** Ensures the architecture can evolve to mobile, multi-user, and cloud deployment without redesigning the autonomous core. Mobile treated as client-only; heavy backend stays on server.
- **Result:** `docs/RUNTIME_PROFILES.md` created with contract compatibility matrix, resource-aware execution profiles, and gap analysis.

## [AF.3] Database Driver — KEEP better-sqlite3
- **Decision:** Keep `better-sqlite3` v13.0.3 as the database driver. The Windows native build blocker is an environment provisioning issue, not an architectural defect. Replacing with `sqlite3` does NOT solve the native build problem and would require rewriting 15 DAOs + 4 migrations. Node.js built-in `node:sqlite` is experimental. `sql.js` has performance risk.
- **Rationale:** 394 tests pass with the current driver. All alternatives either share the same native build requirement or introduce stability/performance risk.
- **Result:** `docs/DATABASE_DRIVER_ARCHITECTURE_DECISION.md` created with full evaluation of 4 alternatives, measured facts, and migration complexity analysis.

## [AF.4] Autonomous Execution Contract
- **Decision:** Freeze the 8-stage execution pipeline (Intent → Context → Plan → Execute → Observe → Verify → Repair → Deliver) and the role-capability matrix (SUPERVISOR: orchestration only; RESEARCHER: read-only; CODER: read+write+terminal; VERIFIER: read-only+test).
- **Rationale:** Provides a stable contract that all future tool additions and capability expansions must comply with, preventing capability policy bypass.
- **Result:** `docs/AUTONOMOUS_EXECUTION_CONTRACT.md` created with state machine, delegation rules, checkpoint/resume contract, repair cycle contract, and workspace isolation contract.

## [AF.5] System Scaling Boundaries
- **Decision:** Document LOCAL (single process + SQLite), STANDARD SERVER (single-node + optional PostgreSQL), and SCALE (PostgreSQL + object storage + queue + workers) as architectural targets. No distributed infrastructure to be implemented now.
- **Rationale:** Ensures current abstractions (DAOs, ToolRegistry, CapabilityPolicy, ResultValidator) do not obstruct future scaling. Identified 7 blocking abstractions that must change for SCALE tier.
- **Result:** `docs/SYSTEM_SCALING_BOUNDARIES.md` created with abstraction readiness matrix, blocking vs non-blocking analysis, and recommended migration priority order.
